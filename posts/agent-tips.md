# Agent 使用技巧：查资料、总结、对比与公式推导

2026 年，AI agent（能自主调用搜索、读写文件、执行命令、多步完成任务的 AI）已经不是新鲜事物。但同一批工具，会用与不会用，效率差距非常大。本文整理几类最高频场景——查资料、总结、代码对比、数学公式——下经过验证的做法，文末附上参考资料。文中的公式就是用 agent 生成、再由本站的 KaTeX 渲染的，算是当场演示。

## 0. 先立规矩：上下文决定上限

agent 每次会话都从零开始，不记得你的项目结构、环境配置和踩过的坑。当前社区的主流做法是把这部分知识固化成"记忆文件"（`AGENTS.md` / `CLAUDE.md` 等），放在仓库根目录，agent 每次进入自动读取。

写记忆文件的要点：

- **一条只说一件事**：简短、无歧义，过时的及时删除——错误的记忆比没有记忆更糟；
- **精准加载，而非堆砌**：无关的上下文会稀释关键信息，反而降低回答质量；
- **写"坑"比写"常识"更有价值**：比如"本机到 GitHub 的 443 端口可能整段不通，先 curl 测连通再动手"，这类信息 agent 无法自己推断。

本站仓库根目录就维护着一份这样的文件，记录了新增文章的固定流程、本地预览的注意事项——本文正是在这套机制的约束下写成的。

## 1. 查资料：把"检索"变成"调研"

直接丢给 agent 一个大问题，得到的往往是一篇四平八稳的泛泛之谈。更有效的做法：

1. **限定范围与时效**。明确"2025 年之后的资料""只看官方文档""中文社区"，比"帮我查查 XX"得到的答案可靠得多。
2. **三段式推进**。先让 agent 列出检索方向和提纲，确认无误后再展开检索，最后汇总。一步到位的长任务，跑偏了只能全部重来。
3. **要求标注来源，并交叉验证**。让 agent 给出每个结论的出处；对关键事实，要求至少两个独立来源相互印证。单一来源的结论一律视为待定。
4. **要对比，不要站队**。调研类需求明确要求"列出不同来源的说法及其分歧点"，而不是"给一个答案"——后者会掩盖领域内的争议。

## 2. 总结：先定结构，再填内容

总结类任务质量差，九成是需求本身没说清。开动前先回答三个问题：

- **给谁看**：给老板的摘要和给自己的笔记是两种文体；
- **多长**：直接限字数或条数，比如"不超过 10 条要点"；
- **什么形式**：要点列表、表格、还是一段话？涉及多项对比时，表格几乎总是优于大段文字。

进阶技巧：

- **长文档分块总结再汇总**：先让 agent 给出全文的目录级概括，确认重点后逐节展开，最后合并。一次性吞下几百页文档，细节丢失不可避免；
- **要求保留原文的数字、引用和术语**，总结最怕的就是悄悄丢信息；
- **每条总结附带"为什么重要"**：区分"压缩"和"复述"，前者才有增量价值。

## 3. 代码对比：先问意图，再问对错

代码是 agent 最擅长的领域之一，但提问顺序有讲究：

1. **给 diff，不给全文件**。让 agent 聚焦在改动上，而不是在几千行无关代码里猜你关心什么；
2. **两步提问**。先问"这段改动的意图是什么"，确认 agent 理解正确后，再问"实现有没有问题"。直接问"有没有 bug"，容易收获一堆不痛不痒的风格建议；
3. **按约束逐项对比**。比较两个方案时，先列好自己的约束（性能、可读性、依赖数量、迁移成本），让 agent 按清单逐项打分输出表格——结论好不好先不论，过程透明可查；
4. **让代码自己证明自己**。能运行的就让 agent 实际跑测试、跑 dry-run；"看起来对"和"是对的"之间隔着一整个 CI。

## 4. 数学与公式：从推导到排版

agent 处理数学有两层用途：**推导**和**排版**，两者都可以直接落地。

排版层面，agent 可以直接产出 LaTeX，配合 KaTeX / MathJax 渲染。行内公式如欧拉恒等式 $e^{i\pi}+1=0$，行间公式如柯西–施瓦茨不等式：

$$\left(\sum_{i=1}^{n} a_i b_i\right)^2 \le \left(\sum_{i=1}^{n} a_i^2\right)\left(\sum_{i=1}^{n} b_i^2\right)$$

推导层面，两个实用技巧：

- **分步推导，每步注明依据**。要求 agent 把证明拆成小步、每步标注用到的定理或已知条件，错误会更容易定位；
- **换个会话当审稿人**。把推导结果丢进一个全新的、不知道原思路的会话，让它只做检查。同一个会话里让 agent 自己查自己，它倾向于顺着原有思路走，查不出方向性错误。

排版上有一个本站真实踩过的坑：Markdown 表格里写绝对值要用 $\vert x \vert$ 而不能用 $|x|$——裸竖线会被 Markdown 解析器当作表格的列分隔符，整个表格都会错乱。表格外的正文中两种写法都能正常渲染。

## 5. 几条通用习惯

- **任务拆小，一步一验收**。方向轻微跑偏就地纠正；完全跑偏就重开会话——会话越长沉没成本越高，重开反而便宜；
- **先方案，后动手**。重要任务先让 agent 出计划，确认后再执行，避免"写完了才发现理解错了"；
- **无副作用验证**。用 dry-run、`--check` 之类的命令先确认权限和环境，再执行真实操作；
- **敏感信息不进对话**。密码、token 不要贴进任何会话，让 agent 通过环境变量或凭据管理器取用；
- **让 agent 把踩过的坑写回记忆文件**。好记性不如烂笔头，这句话对 agent 同样成立——你今天替它踩的坑，明天它还会再踩一遍。
